# LAMPA + Kinozal: идеи, архитектура и план исследования

Статус: предварительная концепция, без изменений на ТВ-приставке.

Дата: 27 октября 2026 года.

Целевое устройство: Xiaomi MiTV-AFMU0 / `twilight`, Android 14, 2 ГБ RAM, ARM 32-bit.

## 1. Цель

Сделать удобный телевизионный интерфейс для поиска раздач Kinozal и передачи выбранной раздачи в TorrServe/TorrServer, сохранив LAMPA как основную медиаоболочку.

Желаемый результат:

- нормальный поиск с пульта;
- категории и фильтры;
- карточки раздач с понятными техническими данными;
- избранное и история;
- кнопка запуска через TorrServe/TorrServer;
- минимум рекламы и лишних переходов;
- работа на Android TV с 2 ГБ RAM;
- отсутствие зависимости от Google TV Home.

По политике конфиденциальности приложения:

- код устройства формируется из Android ID и используется для лицензии;
- логин и пароль Kinozal хранятся локально в зашифрованном хранилище Android;

- сервер лицензирования получает технические данные, IP и сведения о лицензии;
- magnet, название и постер передаются установленному пользователем TorrServe;

Политика: [mnogotv.de/knz/privacy.php](https://mnogotv.de/knz/privacy.php).

Это хороший функциональный референс, но не обязательно подходящая архитектура для нас: приложение зависит от собственного сервера лицензирования и серверной схемы доступа к Kinozal.

## 4. Что такое LAMPA и почему она подходит

Плагин может:

- подключаться к внешнему плееру или TorrServer;
- публиковать отдельный preview-канал Android TV через native bridge, если это поддерживается устройством.

## 6. Варианты доступа к Kinozal

### Вариант A — прямой доступ из плагина

LAMPA обращается к сайту напрямую.

Плюсы:

- нет собственного сервера;
- простая архитектура;
- данные идут напрямую к Kinozal.

Минусы:

- CORS и ограничения WebView;
- cookies и авторизация;
- CAPTCHA и антибот-защита;
- нестабильность зеркал;
- возможная поломка при изменении HTML сайта.

Подходит для прототипа и проверки идеи.

### Вариант B — локальный прокси/API

Схема:

```text
LAMPA-плагин → локальный API → Kinozal → нормализованный JSON → LAMPA
```

API может работать на ПК, NAS, роутере или рядом с TorrServer.

Плюсы:

- контроль над cookies и сессиями;
- можно переключать зеркала;
- можно кэшировать каталог;
- можно нормализовать данные под единый формат;
- можно скрыть сложность HTML и авторизации от телевизора.

Минусы:

- нужно поддерживать отдельный сервис;
- нужно аккуратно хранить учётные данные;
- потребуется настройка адреса API в плагине.

Это наиболее надёжный вариант для постоянного использования.

### Вариант C — использовать существующий сервер приложения Kinozal TV

Теоретически можно исследовать его API или формат запросов. Практически это зависит от того, доступен ли публичный API и разрешает ли автор приложения такое использование.

Плюсы:

- возможно, уже решены зеркала и fallback;
- может быть готовая нормализация карточек.

Минусы:

- API не документирован;
- есть зависимость от чужого сервера;
- может потребоваться лицензия;
- возможны изменения без предупреждения;
- логин и пароль могут проходить через стороннюю инфраструктуру.

Этот вариант требует отдельного read-only исследования APK и сетевых запросов.

## 7. Отдельное приложение или плагин

### Плагин LAMPA

Предпочтительный первый этап.

Оценка:

- прототип экрана и поиска: 2–5 дней;
- рабочая версия с карточками и фильтрами: 1–3 недели;
- прокси, авторизация, TorrServer, кэш и обработка ошибок: 3–6 недель.

Плюсы:

- не нужно делать отдельный лаунчер и плеер;
- можно использовать существующие карточки и навигацию LAMPA;
- быстрый выпуск и откат;
- интерфейс остаётся единым с LAMPA.

Минусы:

- зависимость от API LAMPA;
- плагин выполняется в общем WebView;
- возможны изменения API между версиями;
- нет полноценной песочницы.

### Отдельное Android TV-приложение

Оценка:

- простой клиент: 1–2 месяца;
- качественная версия с авторизацией, кэшем и интеграцией TorrServe: 2–4 месяца.

Плюсы:

- полный контроль над интерфейсом;
- собственная архитектура и обновления;
- можно сделать отдельную лицензионную или бесплатную модель.

Минусы:

- больше кода;
- отдельное управление пультом и фокусом;
- собственная обработка обновлений;
- отдельное тестирование на Android TV;
- больше памяти и ответственности за стабильность.

## 8. Безопасность плагинов LAMPA

Плагин — это произвольный JavaScript, выполняемый внутри LAMPA. Из-за этого он потенциально может получить доступ к:

- локальному хранилищу LAMPA;
- сохранённым настройкам;
- токенам и данным аккаунта;
- сетевым запросам;
- пользовательским данным в WebView.

Собственный плагин лучше хранить в собственном репозитории и устанавливать по собственной ссылке. Для тестов можно использовать локальный HTTP-сервер в домашней сети. Публичные плагины нужно устанавливать только после просмотра исходников.

## 9. Лицензии и использование чужих проектов

- LAMPA и её JavaScript-ядро имеют открытые исходники и собственные условия лицензирования.
- [Настин кинозал](https://github.com/yaroslavrudenko/nastin-kinozal) — полезный визуальный и архитектурный референс, но в репозитории не обнаружен файл лицензии. Использовать его идеи можно, прямое копирование кода требует отдельного разрешения.
- Kinozal TV с mnogotv.de — отдельное коммерческое приложение, привязанное к лицензии устройства. Его интерфейс можно изучать как референс; использование его закрытого API или серверной инфраструктуры требует отдельной проверки разрешений.

## 11. Что не следует делать сразу

- не менять текущую LAMPA до появления прототипа;
- не отключать текущие плагины массово;
- не отправлять логин и пароль на неизвестный публичный прокси;
- не встраивать пароль в URL плагина;
- не делать автоматические изменения через ADB;
- не трогать HDMI-CEC, лаунчер AT4K и Key Mapper ради теста плагина;
- не добавлять десятки тяжёлых расширений на приставку с 2 ГБ RAM.

## 12. Рабочая гипотеза

Наиболее разумный итоговый вариант:

```text
AT4K Launcher
    ↓
LAMPA
    ├── обычные каталоги и просмотр
```

## 14. Локальный read-only прототип

В рабочей папке создан каталог `lampa-kinozal/`:

- `plugin.js` — внешний JS-плагин с защитой от двойной загрузки, экраном поиска, карточкой раздачи, пагинацией и настройками;
- `api-contract.md` — минимальный контракт локального API поиска и явной передачи выбранной magnet-ссылки в TorrServe/TorrServer;
- `mock-results.json` — фиктивные данные для проверки интерфейса;
- `README.md` — порядок локального запуска и ограничения прототипа.
- `LAMPA-plugin-docs.md` — ссылка на полный официальный справочник разработки плагинов LAMPA с перечнем разделов.

Без настроек плагин работает в режиме `mock`: сетевых запросов нет. Режим `proxy` использует только явно заданный HTTP(S)-адрес и отправляет GET-запросы поиска. Передача в TorrServer выполняется только после выбора карточки и нажатия кнопки; фоновой отправки, авторизации Kinozal и ADB-действий нет.

Прототип опирается на документированные точки расширения LAMPA: `app:ready`, `Lampa.Component`, `Lampa.Activity`, `Lampa.SettingsApi`, `Lampa.Storage`, `Lampa.Reguest`, `Lampa.Modal` и `Lampa.Scroll`. При изменении API LAMPA нужно сначала сверить версию приложения с официальной документацией и руководством миграции.

Главная неопределённость — не интерфейс, а доступ к Kinozal: авторизация, зеркала, антибот-защита и стабильный способ получения данных. Поэтому первым техническим экспериментом должен быть небольшой read-only прототип поиска, а не полноценная установка или изменение приставки.

## Сессия продолжения — переход на штатную архитектуру LAMPA

По официальному `UPGRADE.md` выяснено, что старый ручной DOM (`div.card` внутри собственного `Lampa.Scroll`) не создаёт навигационную модель LAMPA. Штатная схема строится через `Lampa.Maker.make('Main')`, затем `Main.build()` создаёт `Line`, а `Line` создаёт `Card`; обработчики пульта подключаются через `onInstance` и `onlyEnter`.

В `plugin.js` добавлен этот путь для экрана топ-раздач. Результаты теперь передаются в стандартную структуру `Main → Line → Card` с параметрами карточек; старый экран оставлен резервным для сборок без `Lampa.Maker`. Синтаксис корневого и вложенного `plugin.js` проверен через `node --check`.

Официальная опора: `UPGRADE.md`, разделы «Модульные классы», «Пример создания компонента Main», «Пример создания класса Card» и «Структура ответов API».
